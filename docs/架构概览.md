# minicode 架构概览

minicode 是一个命令行编程 Agent：

```text
用户提出目标
→ 模型判断下一步
→ 调用工具
→ 本地程序校验、审批并执行
→ 把结果交还模型
→ 验证结果
→ 完成任务
```

模型负责决策，本地运行时负责安全执行。

## 1. 整体架构

```text
CLI / TUI
    ↓
Agent Runtime
    ├─ Agent Loop：持续调用模型
    ├─ Plan：保存复杂任务步骤
    ├─ Tool Registry：参数校验、超时、重试
    ├─ Permission：写操作审批
    ├─ Checkpoint：文件修改失败回滚
    ├─ Audit：记录调用、审批和结果
    └─ Session：保存对话和用量
    ↓
工具
    ├─ 文件读取、搜索
    ├─ 文件写入、编辑
    ├─ Shell 命令
    ├─ MCP 工具和 Resources
    ├─ Skills
    └─ 子 Agent
```

模型可以选择：

```text
本地：Ollama + qwen3:8b
远程：DeepSeek
```

两者使用同一套 Agent Loop 和工具系统。

## 2. Agent Loop

每轮模型可以：

- 直接回答。
- 调用一个工具。
- 同时调用多个只读工具。
- 根据工具结果继续调用其他工具。
- 遇到失败后修改参数或更换方案。
- 最终停止调用工具并给出答案。

系统有限制：

- 最多迭代次数。
- 最多工具调用数。
- 重复调用阈值。
- 连续错误阈值。
- 整轮执行时间限制。

如果持续重复或没有进展，会触发 LoopGuard，禁止继续调用工具并强制收尾。

## 3. Tool Registry

所有工具都经过统一 Registry：

```text
模型生成参数
→ JSON Schema 校验
→ 权限判断
→ 超时控制
→ 执行工具
→ 结果校验
→ 错误分类
→ 必要时重试
```

例如模型调用：

```json
{
  "name": "read_file",
  "arguments": {}
}
```

因为缺少 `path`，Registry 会在执行前拒绝：

```json
{
  "ok": false,
  "error": {
    "code": "INVALID_TOOL_ARGUMENTS",
    "retryable": false,
    "message": "缺少必填参数 path"
  }
}
```

工具不会真正运行。

## 4. 权限系统

工具按副作用分类。

只读工具通常直接执行：

```text
read_file
list_dir
grep
glob
```

写操作执行前需要审批：

```text
write_file
edit_file
run_command
MCP 工具（默认全部逐次审批）
```

高风险操作不能选择“本会话永久允许”，只能逐次批准。

MCP annotations 只影响执行属性，不单独决定是否审批：

```text
readOnlyHint: true  → 只读
destructiveHint     → 高风险
没有明确注解         → 保守地视为写操作
```

`readOnlyHint` 只能说明工具不修改服务端状态，不能保证调用参数不会携带本地数据外发。因此未配置时
MCP 默认使用 `approval: always`；只有对可信 Server 显式配置 `writes` 或 `never` 才会跳过部分审批。

## 4.1 Prompt Injection 边界

文件、命令输出、MCP、Resource、`structuredContent` 和子 Agent 调查结果都按不可信外部数据处理：

```text
外部结果
→ 添加来源和数据边界
→ 检查明显的目标覆盖、工具诱导和密钥外传片段
→ 可疑片段只保留 SHA-256 证据
→ 安全结果作为 role=tool 交给模型
```

MCP 工具描述及参数说明也会在发现阶段清洗；可疑描述不会原样加入 Tool Schema。该检测只能降低常见
攻击面，不能保证识别所有自然语言变体，最终仍由权限审批、参数校验、工作区限制和审计控制副作用。

## 5. Checkpoint

Checkpoint 是文件修改前的临时恢复点。

```text
修改文件前
→ 保存旧内容和 SHA-256
→ Agent 修改文件
→ 执行验证
```

验证成功：

```text
checkpoint commit
→ 保留新文件
→ 删除临时旧版本
```

验证失败：

```text
checkpoint rollback
→ 恢复原文件
→ 删除 Agent 新建的文件
```

如果用户在 Agent 修改后又手工修改文件，SHA-256 会不一致，系统拒绝覆盖并报告冲突。

Checkpoint 只保护文件工具，不保护：

- Shell 命令副作用。
- MCP 写操作。
- 数据库。
- 网络请求。

它目前只存在内存，任务成功或进程退出后不能用于 `/undo`。

## 6. Verification

工具执行成功不代表任务完成。

系统要求修改后进行验证，例如：

```text
重新读取文件
运行测试
运行构建
检查命令退出码
检查文件 SHA-256
```

成功的 `run_command` 被视为一个验证边界，可以提交当前文件 checkpoint。

如果命令退出码不是 0：

```text
工具返回失败
→ 当前文件批次回滚
→ 错误交给模型
→ 模型修复后重新尝试
```

Plan 中的步骤标记为 `completed` 或 `blocked` 时，也必须填写验证证据。

## 7. Audit 审计

每次工具调用都会生成：

```text
executionId
toolCallId
startedAt
```

审计链：

```text
tool_use
→ permission_request
→ permission_response
→ retry
→ tool_result
```

记录内容包括：

- 工具名。
- 脱敏参数。
- 参数 SHA-256。
- 审批结果。
- 重试原因。
- 成功或失败。
- 结果预览。
- 执行时间。

daemon 模式写入：

```text
.sessions/<sessionId>.events.jsonl
```

单进程模式写入：

```text
.sessions/<sessionId>.audit.jsonl
```

审计用于追踪和回放，不用于恢复旧文件或崩溃续跑。

## 8. MCP

MCP Server 连接后，minicode 会自动发现它提供的工具。

```text
连接 MCP Server
→ listTools()
→ 注册为 mcp__server__tool
→ 加入 Tool Registry
```

支持：

- stdio。
- Streamable HTTP。
- `structuredContent`。
- Resources。
- Resource Templates。
- MCP 权限 annotations。

Resource 使用方式：

```text
list_mcp_resources
→ 获得 Resource URI
→ read_mcp_resource
→ 按需读取正文
```

Resource 不会全部塞进 Prompt。

## 9. Plan

复杂任务可以建立计划：

```text
pending
in_progress
completed
blocked
```

例如：

```text
1. 定位问题          completed
2. 修改代码          in_progress
3. 运行测试          pending
```

Plan 用来减少目标漂移和重复执行，但不是严格业务状态机。状态主要由模型更新，目前只保存在运行时内存。

## 10. Session 与上下文

Session 保存：

- 用户与模型的对话消息。
- 工具调用和工具结果。
- token 用量。
- notes。

上下文过长时，系统会压缩较早的执行历史，同时尽量保留：

- 原始目标。
- 已确认事实。
- 失败方案。
- 验证结果。
- 当前进度。

本地 Qwen 默认使用 16384 上下文，并在使用约 75% 时尝试压缩；DeepSeek 默认压缩阈值为 40000。

# 工作流程示例

## 示例一：读取并解释代码

用户：

```text
帮我看看登录失败的原因
```

执行流程：

```text
1. 模型调用 grep 搜索登录代码
2. Registry 校验 pattern
3. grep 是只读工具，不需要审批
4. 执行搜索
5. 审计记录 tool_use 和 tool_result
6. 模型调用 read_file 读取相关代码
7. 根据真实文件内容分析
8. 给出原因和修改建议
```

这次没有修改文件，所以不创建 checkpoint，也不需要写操作审批。

## 示例二：修改文档并验证

用户：

```text
修改 README，加入本地 Qwen 启动说明
```

完整流程：

```text
1. 模型调用 read_file 阅读 README
2. 模型生成修改内容
3. 调用 edit_file
4. Registry 校验 path、old_str、new_str
5. 权限系统询问用户
6. 用户批准
7. 创建 checkpoint，保存 README 原内容
8. 执行 edit_file
9. 审计记录修改结果
10. 模型重新读取 README
11. 运行检查命令
12. 验证成功
13. checkpoint commit
14. 保存 Session
15. Agent 总结修改内容和验证结果
```

如果第 11 步验证失败：

```text
run_command 返回非零退出码
→ checkpoint rollback
→ README 恢复原内容
→ 错误交给模型
→ 模型修改方案后重新尝试
```

## 示例三：MCP 查询订单

用户：

```text
查询订单 ORDER_123 是否发货
```

执行流程：

```text
1. 模型选择 get_order_detail
2. Registry 校验 order_id
3. MCP annotations 声明 readOnlyHint=true
4. 默认仍请求单次审批，防止参数携带本地敏感信息外发
5. 用户批准后，MCP Server 查询订单系统
6. 返回 structuredContent
7. 结果标记为不可信数据并隔离可疑指令
8. 审计记录 executionId 和结果预览
9. 模型根据 shipping_status 回答
```

如果用户要求执行退款，退款工具属于写操作：

```text
调用退款工具
→ 参数校验
→ 权限审批
→ 用户批准
→ MCP 执行
→ 审计记录结果
```

MCP 外部副作用不能由本地 checkpoint 回滚，最终安全性仍由业务 Server 的权限、幂等和规则保证。

## 示例四：工具持续失败

模型连续使用相同参数调用同一个工具：

```text
第 1 次失败
第 2 次失败
第 3 次仍得到相同结果
```

系统检测到：

```text
repeated_tool_call / no_progress
```

然后要求模型：

```text
禁止原样重复
回到已验证事实
修改参数、换工具或调整计划
```

如果仍然没有进展：

```text
LoopGuard 触发
→ 禁止继续调用工具
→ 未提交文件 checkpoint 回滚
→ Agent 说明已完成内容、失败原因和下一步
```

## 总结

minicode 已经形成完整闭环：

```text
模型决策
→ 工具调用
→ 参数校验
→ 权限审批
→ 安全执行
→ Checkpoint 保护
→ Verification 验证
→ Audit 审计
→ Session 保存
→ 最终回答
```

第一次了解项目先阅读本文；需要查看工具参数和权限时阅读[工具手册](工具手册.md)；需要查看具体源码
实现时再阅读[实现说明](实现说明.md)。
